新建任务会话框：实现方案对比

目标：完整保留现有普通会话 / 智能体 Composer 能力，仅在第一次发送时创建会话，并将当前 Tab 切换到该会话。

A · 延迟创建适配器（推荐）

抽取共享 Composer 装配层，并给发送控制器注入“确保会话存在”的回调。输入阶段不产生空会话，首次发送才创建。

优点

  • 完全符合发送时创建
  • 复用现有完整能力
  • 不会污染历史列表
  • 失败可保留草稿

代价

  • 需小幅重构 Composer 边界
  • 需严谨处理创建与发送状态
B · 进入页面即创建占位会话
进入 / 切换资源
↓ 立即创建
空 Topic / 空 Session
↓
直接挂载现有页面 Composer

B · 预创建占位会话

复用现有页面前置创建流程，先获得 Topic / Session，再渲染原 Composer。

优点

  • 代码改动相对少
  • 现有 Composer 几乎不变

问题

  • 不是“发送时创建”
  • 切换模式可能产生空会话
  • 需额外清理占位记录

C · 独立草稿 Composer

为新建任务页单独实现一套输入、附件、模型、工具和发送逻辑，再转交正式会话。

优点

  • 页面逻辑独立
  • 短期可自由定制 UI

问题

  • 重复大量业务逻辑
  • 长期容易与现有 Composer 漂移
  • 维护和测试成本最高
推荐结论

采用 A：页面级延迟创建适配器

它是唯一同时满足“功能保持一致”“发送时才创建”“当前 Tab 切换”且不复制业务逻辑的方案。重构只服务于这次需求：把现有页面内的 Composer 装配能力下沉为共享边界，不改 Main Process 的消息持久化与流式发送协议。
