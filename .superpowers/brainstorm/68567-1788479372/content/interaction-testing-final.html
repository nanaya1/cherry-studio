方案 A · 页面交互与验收

最终页面不设计第二套会话框。视觉、快捷键、附件、模型与工具行为均来自现有 Composer。

交互约束

  • 切换“普通会话 / 智能体任务”时，各自草稿独立保留，不互相覆盖。
  • 普通会话默认选择沿用现有规则；用户可在发送前更换 Assistant。
  • 智能体任务默认不选择 Agent；选择后才启用依赖 Agent 的模型、Workspace 和工具。
  • 创建与发送期间 Composer 进入现有忙碌态，禁用资源切换和重复发送。
  • 错误通过现有全局错误反馈机制展示，不新增页面专属错误系统。
  • Tab 就地切换后，页面标题与侧栏历史由现有会话元数据刷新机制更新。
预计改动范围

最小、可追溯的前端改动

  • NewTaskPage：由视觉占位替换为两种真实 Composer 宿主。
  • 共享 Composer 变体：抽取当前页面内可复用的装配参数，不改核心 UI。
  • Draft Orchestrator Hook：新增首发创建、in-flight 锁、Tab 就地切换。
  • HomePage / AgentPage：只改为消费抽取后的共享接口，行为保持原样。
  • i18n：仅补充确实缺少的提示文案；优先复用现有键。
  • Main / DB：预计零改动；若实施调查发现现有公开接口无法承载，会先停止并说明，不做下游绕过。

验收测试

  1. 普通模式按既有优先级显示默认 Assistant，并可切换。
  2. Agent 模式初始未选择，选择后完整 Composer 能力可用。
  3. 仅输入文字、仅添加有效附件、文字加附件均可按现有规则发送。
  4. 第一次发送只创建一个 Topic / Session，只提交一条用户消息。
  5. 成功后当前 Tab URL 精确切换，新页面能显示首条消息并继续接收流。
  6. 创建失败或流打开失败时不跳转、不清空草稿。
  7. 快速双击发送不会重复创建或重复提交。
  8. 模式切换后两边草稿和选择状态独立保留。
  9. 现有 Home Chat 与 Agent Chat Composer 回归行为不变。
  10. 运行聚焦测试、pnpm lint，并检查格式、类型和 i18n。
最终设计

只新增草稿到会话的桥接层

页面、Composer、数据源和 Main 流处理均优先复用；不存在的仅为“首发延迟创建 + 当前 Tab 接管”能力。
