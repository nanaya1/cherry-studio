Cherry Studio 沙箱与远端运行整体升级方案

基于当前 meacowork 分支源码的只读架构分析 · 2026-09-07 · 本报告不包含业务源码修改

一、执行摘要

推荐结论：采用“桌面端控制面客户端 + 独立远端执行控制面 + 沙箱 Worker”三层架构；在现有 AgentSessionRuntimeDriver 上新增 Remote Runtime 路由，复用 JobManager、消息持久化和审批 UI，但将远端任务身份、租约、事件、审批、取消确认与制品存储升级为服务端权威状态。不建议 Electron 直接 SSH 或直接连接 Docker Socket。
可复用 6 项Runtime 抽象、DSH 沙箱、JobManager、审批注册、resume token、ApiGateway
核心缺口 7 项Transport、Worker 租约、持久事件、远程审批、取消确认、制品、审计
推荐 5 个 Wave先协议与 Mock Worker，再 POC、审批、安全、生产化
P0 原则本地能力不回归；远端默认最小权限、失败关闭

三、现状关键问题

  1. 无统一远端 Transport：现有 connection 只有 send/events/reconcile/close，缺少 endpoint、worker、lease、heartbeat、reconnect cursor、远端任务 ID。
  2. 沙箱能力不可协商：上层只看到 permission mode，看不到 landlock/ACL/容器/microVM 是否真实生效及降级等级。
  3. 无人值守审批断链：headless 运行无 renderer 时直接拒绝；现有文档已将其标记为关键外部运行缺口。
  4. 权限与审批耦合：DSH 的 bypassPermissions 同时把沙箱提升为 danger-full-access，不能用于解决远端无人值守。
  5. 取消不等于停止：JobManager 超时后可把 DB 行置终态，但 handler 仍可能运行；远端场景必须要求 Worker ACK 与沙箱销毁证明。
  6. 恢复状态未统一：Job retry、Runtime resume token、消息 continuation 是三套独立机制。
  7. 三类 Gateway 概念分散：模型 API 网关、DSH gateway 投影、OpenClaw gateway 不共享任务、审批和沙箱协议。

4.1 模块边界

模块职责禁止承担
Desktop RemoteRuntimeDriver提交 Run、订阅事件、发审批、取消、重连不直接创建容器，不持有 Worker 管理凭证
Execution Control Plane任务权威状态、策略快照、Worker 调度、租约、审计、幂等不执行用户命令
Worker Agent注册能力、领取租约、创建沙箱、转发事件、销毁资源不自主扩大权限，不长期保存用户凭证
Sandbox Provider文件、进程、网络、资源和生命周期隔离不决定业务审批策略
Artifact Store输入快照、输出制品、日志归档、校验和不作为实时事件总线

4.2 推荐技术形态

  • 控制协议：HTTPS REST 负责命令，WebSocket 或 SSE 负责按序事件；事件必须带 runId + attempt + sequence。
  • 控制面：建议先做模块化单体服务，PostgreSQL 持久化，Redis 仅做通知/短期队列；避免初期拆微服务。
  • Worker：主动向控制面建立出站连接，避免公网暴露 Worker；基于租约领取任务。
  • 沙箱：P0 用 rootless 容器完成闭环；高风险代码执行再升级到 Firecracker/Kata 等 microVM。DSH 可作为沙箱内 Agent Runtime。
  • 对象存储：S3 兼容存储保存 workspace 输入包、artifact、日志归档；上传下载均使用短期签名 URL。

七、权限与安全设计

核心原则：“是否需要审批”与“沙箱允许做什么”必须分离。远端运行不得通过 bypassPermissions 解决无人值守问题。
威胁等级缓解措施验证
伪造 Worker 或桌面身份高OIDC 用户身份 + mTLS Worker 证书 + 短期任务令牌，令牌绑定 run/attempt/audience错误证书、过期令牌、跨任务重放均拒绝
策略在传输或执行中被篡改高控制面生成不可变 policy snapshot 和 digest；Worker 校验后执行并回报 digest篡改策略集成测试
提示注入触发危险工具高入口 provenance、tool allow/deny、非交互确定性策略、危险操作持久审批对抗用例 + 越权工具拒绝
凭证泄露到日志/制品高短期凭证、secret mount、日志脱敏、制品分类与下载授权密钥 canary 扫描
逃逸或宿主资源耗尽高rootless、只读根文件系统、seccomp、no-new-privileges、cgroup 配额、网络默认拒绝逃逸基线与资源限额测试
重复执行造成副作用中高idempotency key、attempt/epoch、工具副作用分类、恢复时人工/策略判定断线与 Worker 故障注入测试

八、方案选型与决策

方案优势主要问题结论
A. Electron 直接 SSH 到服务器POC 快、组件少凭证散落、无统一任务状态/审批/审计、断线恢复困难、扩容差不推荐
B. 控制面 + Worker + 容器沙箱与现有 Driver/Job 体系匹配；安全、审计、扩容、恢复可治理需新增服务端与 Worker，初期工程量较大推荐
C. 直接采用 K8s Job调度与资源隔成熟审批/事件/会话仍需自建；开发及私有化门槛高，产品与 K8s 强耦合作为 Worker 后端
D. Serverless 沙箱供应商上线快、无需运维底层供应商锁定、数据合规和国内网络风险、成本不可控可做适配器
架构决策：选择 B，控制面先采用模块化单体，Worker 的 SandboxProvider 保留多后端接口；P0 默认 rootless 容器，K8s Job/Serverless 作为后续适配器。接受的代价是需要维护服务端状态与 Worker 协议。撤销条件：若产品只服务单机单用户且永远无共享/审计/伸缩需求，可降级为本地容器；若单集群并发长期超过 500 个沙箱或有强多租户隔离要求，再升级为 K8s + microVM。

十一、验收指标与发布门禁

  • 功能：本地运行全部保持；远端创建、流式输出、工具调用、审批、取消、制品下载、恢复均闭环。
  • 可靠性：事件至少一次投递且客户端幂等；控制面重启后 Run 可恢复；租约失效不产生并发双执行。
  • 安全：默认网络拒绝；非授权 mount/命令/工具 100% 拒绝；所有危险工具决策可追溯。
  • 性能建议：创建到 assigned P95 ≤ 2 秒（有空闲 Worker）；事件端到端 P95 ≤ 500ms；取消 ACK P95 ≤ 5 秒，完整销毁 P95 ≤ 30 秒。
  • 可观测：run_success_rate、queue_wait、sandbox_start、event_lag、approval_wait、lease_expired、orphan_count、cancel_latency。
  • 发布：feature flag 按用户/租户灰度；本地运行始终为回退路径；远端故障禁止自动降级为本地危险执行。

十二、当前明确不应做的事项

  • 不要把当前 ApiGateway 的进程内 token 当作远端 Worker 身份。
  • 不要通过 bypassPermissions 让远端/headless 工具“先跑起来”。
  • 不要让 Electron 保存 SSH 私钥、Docker 管理权限或 Kubernetes admin kubeconfig。
  • 不要只依赖数据库 cancelled 状态而忽略沙箱实际是否终止。
  • 不要把实时事件全文直接写入主消息表；应先进入 RunEvent，再由适配层投影到会话消息。
  • 不要在 P0 同时支持容器、K8s、microVM 和多云；先完成一个安全后端的闭环。

十三、下一步建议

建议立即启动 Wave 0：先冻结共享协议与状态机，创建 Mock Remote Worker，证明现有 AgentSessionRuntimeService 能在不破坏本地 Claude/Pi/DSH 的前提下消费远端事件。随后再决定控制面具体落在现有平台服务还是独立仓库。首轮不引入真实容器依赖，可将验收目标定为：同一 Agent 会话可选择 Local 或 Mock Remote；流式文本、工具事件、取消和断线续传的 contract tests 全部通过。
证据范围：Agent Runtime 接口与注册、DSH composition/Bridge、AgentSessionRuntimeService、JobManager 类型与 Agent Task handler、ApiGateway 内部身份、Channel headless 与安全设计文档。结论属于源码静态架构评估；尚未进行远端环境 POC、容量压测或沙箱逃逸测试，因此生产可用性仍需 Wave 1-4 验证。
